# 05 — Release packaging

Proposed on 2026-11-15. This spec was split out of an earlier, larger release spec in
its round-3 review; the publication itself is `docs/06-publish-on-github.md`. It is an
increment about packaging, not behaviour: no line of `src/` changes.

Implemented on 2026-11-15. Criteria 1–7 are verified; the publication is still pending in
`docs/06`.

## Goal

The plugin is legally usable, correctly described, and proven on every push: an MIT
licence, a manifest that a package manager and the pi gallery can read, a test that
keeps the manifest from regressing, and a CI workflow that runs typecheck and the suite.
Who publishes it, and how the repository gets there, is `docs/06`.

## Non-goals

- **No** publication of any kind. The docs scrub, the index changes, the commit-identity
  rewrite, the GitHub repository, the push, the tag, the release and the live install
  are `docs/06-publish-on-github.md`.
- **No** npm publish and no entry in the Pi package gallery. The `pi-package` keyword is
  metadata for later; it has no effect without an npm package.
- **No** `.gitignore` entry for the workstation files. They are still tracked here; they
  leave the index in `docs/06`.
- **No** `CHANGELOG.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, issue or PR templates.
- **No** lint, coverage reporting, CI matrix, Dependabot or release automation.
- **No** rename of the package or of the branch.
- **No** behavioural change: no fix for the known limits (`Main` after `--resume`,
  `/agent <name>`, picker, `tools` adoption, package tier), no new key, no new option.

## Testing

| File | Case | What it proves |
|---|---|---|
| `test/package.test.ts` | `manifest is not private` | `private` is absent or `false`, so the package is installable as a package rather than only as a path |
| | `manifest carries the release metadata` | `version` is not `0.0.0`, and `description`, `license`, `keywords` (`pi-package`), `engines.node` and `repository.url` are filled |
| | `the files allowlist covers every extension path` | each entry of `pi.extensions` resolves inside a `files` entry — a narrowed allowlist cannot silently ship a package without its entry point |
| | `LICENSE is MIT and matches the license field` | the file exists, its first line is `MIT License`, and `package.json` says `MIT`; the two cannot drift |
| `test/agents.test.ts`, `test/apply.test.ts`, `test/prompt.test.ts`, `test/state.test.ts`, `test/extension.test.ts` | the 54 existing cases | they keep their names and stay green: packaging changes no behaviour, and criterion 2 shows no test file was edited |

The rest of this increment is proven by the commands in `## Acceptance criteria`: the
metadata, the tarball contents and the licence are only decidable by running them. The
four new cases exist to keep the manifest from regressing afterwards, not to prove the
packaging happened.

No case needs network, a model call or a real pi session. `npm pack --dry-run` writes
nothing to the working tree; if a future case needed a tarball, it has to build it in
`os.tmpdir()`.

## Risks and alternatives

- **`files` can hide a file the extension needs at runtime.** The
  `the files allowlist covers every extension path` case proves the *entry point* is
  inside the allowlist. A runtime import from outside `src/` is caught by nothing at test
  time — only a live install would notice. The case guards against narrowing `files`; it
  does not prove completeness.
- **Removing `private` opens the door to `npm publish`.** The name belongs to another
  publisher, so an attempt is rejected with a 403 rather than succeeding under the wrong
  name. The field is removed because `private: true` contradicts a public release.
- **The `pi-package` keyword promises gallery discovery that does not exist** until an
  npm package is published. It is metadata for that day, and the README status line says
  so.
- **The pi bump is verified in a scratch copy, not in this tree.** That scratch run on
  1.5.2 was green on 2026-11-15 (typecheck, `Tests  54 passed (54)`). The increment
  repeats it as criterion 1 and 2, so a silent drift shows up there.
- **`npm ci` needs a committed, lockfile-synchronised `package.json`.** If the manifest
  was hand-edited without a following `npm install`, CI fails at the first step while
  everything is green locally. Stage 4 runs the same three steps locally for that reason.
- **The README points at a repository that does not exist yet.** Stage 5 writes the git
  install URL and a *Status* paragraph that calls the repository public; the manifest
  carries `repository`, `homepage` and `bugs`. All four answer 404 until `docs/06` creates
  it. The window is minutes, and the README is where the command belongs; `docs/06`
  records the same window. Without this note, the prose claim of publicness would be the
  only unbacked sentence in the file.
- **Rejected alternative: keep `1.3.0`.** A public plugin pinned to a release two minors
  behind what users install today would have to be re-verified on its first day.

2. **The manifest guard** — new `test/package.test.ts`. Owner: implementer.
   Unlike `test/agents.test.ts` and `test/extension.test.ts`, this file builds **no**
   `mkdtempSync` tree: it reads the real project root, because the manifest and the
   licence file are the artefacts under test. Anchor them once in module scope,

   `const LICENSE = new URL("../LICENSE", import.meta.url);`, read with

   - `manifest is not private` — `expect(manifest.private ?? false).toBe(false)`; the

     `"0.0.0"`, `description`, `license` and `engines.node` are non-empty strings,

### What could go wrong

- **Most likely break: the lockfile after the pi bump (stage 3).** `npm install` may lift
  transitive versions beyond the pi package, and the scratch verification installed 1.5.2
  without this repository's lockfile history. Symptom: typecheck or a case red in stage 3,
  or `npm ci` red in stage 4 with `EUSAGE … lock file … does not satisfy`. Both stages run
  those commands for exactly this reason; a red is a report, not a silent retreat to 1.3.0.
- **The `files` allowlist can produce a different file count than expected.** npm always
  adds `package.json`, `README*` and `LICENSE*`; `package-lock.json` stays out. Stage 1's
  `--json` proof prints the eight paths, so an extra entry is visible before the commit.
- **`git status --short test/` is a pre-commit check.** It proves "no existing test file
  was edited" only while the work is uncommitted; after the commit the same command is
  empty for the wrong reason. Criterion 7 therefore re-checks it against the commit
  itself, `git show --name-only --format= HEAD -- test/`, instead of pointing at another
  spec: `docs/06`'s criterion 7 looks at a different commit and would print the whole
  packaging commit, not a `test/` path.
